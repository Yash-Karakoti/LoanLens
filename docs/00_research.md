# Research and reference review

Research date: 2026-11-16. This is a curated review of relevant public projects, their available source, and primary documentation. It is not an exhaustive list of every GitHub repository, a universal ranking of the best code, or an independent reproduction of other authors' metrics. No external accuracy claim is used as a result of this project.

## Main conclusions

1. The requested dataset is available directly from the original competition organizer. A live HTTP request returned 200 and the CSV parsed as 614 applications with the expected 13 columns. Record the actual downloaded bytes, SHA-256, source URL, and download time in the dataset manifest; keep raw data immutable.
2. The label is historical approval/rejection. It is not repayment or default. This assistant can study consistency with recorded screening decisions; this dataset cannot demonstrate reduced non-performing assets, establish creditworthiness, or validate actual bank risk reduction.
3. Several close-looking repositories contain preprocessing leakage despite attractive dashboards or broad feature lists. Use the primary library documentation as the methodological standard and keep every fitted transform inside cross-validation pipelines.
4. A simple three-tab interface is sufficient: individual screening and explanation, batch screening, and model evidence. Show probability, threshold, reasons, missing-input notices, and a human-review reminder together. Avoid invented credit scores and unsupported risk grades.
5. Research references inform the design. This project does not copy external application code or import anyone else's trained artifact. Other repositories' licenses do not establish ownership or redistribution rights over the dataset.

## Dataset provenance and units

- Original organizer problem: [Analytics Vidhya — Loan Prediction](https://www.analyticsvidhya.com/datahack/contest/practice-problem-loan-prediction-2/). Its problem description explicitly identifies mortgage approval/rejection as the task.
- Verified direct organizer CSV: [train_u6lujuX_CVtuZ9i.csv](https://datahack-prod.s3.ap-south-1.amazonaws.com/train_file/train_u6lujuX_CVtuZ9i.csv). An independent PowerShell `Invoke-WebRequest` check during research returned HTTP 200; `ConvertFrom-Csv` read 614 data rows and these columns: `Loan_ID`, `Gender`, `Married`, `Dependents`, `Education`, `Self_Employed`, `ApplicantIncome`, `CoapplicantIncome`, `LoanAmount`, `Loan_Amount_Term`, `Credit_History`, `Property_Area`, `Loan_Status`.
- Public backup mirror: [Architectshwet — original CSV](https://github.com/Architectshwet/Loan-prediction-using-Machine-Learning-and-Python/blob/master/data/train_u6lujuX_CVtuZ9i.csv). A live request to its raw URL also returned HTTP 200 and parsed 614 rows with the expected columns. Root directory inspection found no license file; do not infer a data license from public availability.
- Organizer tutorial and data description: [Deploying machine learning models using Streamlit](https://www.analyticsvidhya.com/blog/2020/12/deploying-machine-learning-models-using-streamlit-an-introductory-guide-to-model-deployment/). This identifies loan amount in thousands and term in months. A tutorial is useful for understanding the original schema, but its training implementation is not adopted.

Currency and monthly-income interpretation are assumptions where the original download lacks a complete authoritative currency statement. Keep them explicit in `ASSUMPTIONS.md` and the form. EMI requires converting `LoanAmount * 1000` to principal, using the term in months and an assumed annual interest rate divided by 12. The original data contains no observed interest rate. EMI and balance income are illustrative engineered affordability features, not bank quotes. A zero-interest implementation must use principal divided by months; zero or negative term must not silently cause division by zero.

The requested class-weight/SMOTE experiment generates resampled training examples only inside training folds. These are algorithmic samples, not newly collected applicants and not additions to `data/raw` or evaluation data.

## Primary methodology references

| Source | Decision supported in this project |
|---|---|
| [scikit-learn — Common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html) | Split before fitting, never fit preprocessing on test data, and put fitted transformations in a pipeline so CV refits them inside each fold. |
| [imbalanced-learn — Common pitfalls](https://imbalanced-learn.org/stable/common_pitfalls.html) | Resampling before a split leaks information and distorts evaluation prevalence. Resample only the training portion of each fold. |
| [scikit-learn — Decision threshold tuning](https://scikit-learn.org/stable/modules/classification_threshold.html) | Probability estimation and the screening decision are separate. Tune a cost-based threshold using training validation or out-of-fold predictions, never the final test set. |
| [SHAP — Waterfall plot](https://shap.readthedocs.io/en/latest/example_notebooks/api_examples/plots/waterfall.html) | A local waterfall explains the path from the background expected model output to one prediction. Label units correctly; some tree/linear explainers use log odds rather than probability. |
| [SHAP — Explanation object](https://shap.readthedocs.io/en/latest/generated/shap.Explanation.html) | Track feature names, values and baseline together. Check that baseline plus contributions reconstructs the explained output in the same output space. |
| [Fairlearn — Common fairness metrics](https://fairlearn.org/main/user_guide/assessment/common_fairness_metrics.html) | Predicted selection rates and error rates by group are diagnostic. They are not proof of fairness or a legal certification. Group sample sizes and undefined denominators must remain visible. |

Approval is the positive class. A false positive is a predicted approval for a historically rejected applicant; a false negative is a predicted rejection for a historically approved applicant. Neither error establishes default or repayment. Any cost ratio used for threshold tuning is a documented scenario assumption, not measured bank loss. A high approval-class F1 can coexist with poor rejected-applicant recall; therefore inspect class-level errors, balanced performance and a majority-class baseline too.

Gender and marital status should remain available for auditing. Excluding them from model inputs is a design choice, not a guarantee that proxy discrimination disappears. Small holdout groups, missing group labels and correlated features limit conclusions. SHAP describes associations learned by a particular model relative to a background; it does not establish causality or a reliable action that changes real loan eligibility.

## UI references and design choices

1. [Loan eligibility checker screenshots](https://github.com/preransai/loan-eligibility-checker/tree/main/docs/screenshots) and [its app source](https://github.com/preransai/loan-eligibility-checker/blob/main/app.py): closest domain reference. The source groups the form into income, loan, and applicant sections, separates batch scoring from model evidence, and labels terms in months. The screenshot inventory includes approved/rejected, batch, dataset, fairness and insights views. This research inspected the app source and screenshot inventory; it does not claim a full visual/usability audit of that app.
2. [Streamlit finance gallery](https://streamlit.io/gallery?category=finance): a curated visual discovery starting point, not evidence that any gallery model is appropriate for lending.
3. [Streamlit layouts and containers](https://docs.streamlit.io/develop/concepts/design/layouts-and-containers): use native forms, columns, tabs and expanders. Keep the result and its reasons adjacent; progressively disclose detailed model evidence.
4. [Streamlit app design best practices](https://docs.streamlit.io/develop/concepts/design/best-practices): maintain consistent visual hierarchy, readable tables, responsive layout and deliberate loading behavior. Use APIs supported by the installed version rather than assuming the newest documentation matches it.
5. [Google PAIR — Explainability and trust](https://pair.withgoogle.com/chapter/explainability-trust): give users enough context to interpret a model output, distinguish general system information from the specific prediction explanation, and avoid unsupported confidence claims. [PAIR patterns](https://pair.withgoogle.com/guidebook-v2/patterns) favors concise explanations and progressive disclosure.

Selected visual direction: a restrained finance workspace with a light background, dark navy headings, teal primary action, clear section labels, bordered evidence panels, and readable charts. Status always uses text in addition to color. The probability must be labeled as a model estimate of historical approval, not a repayment probability. The trained decision threshold and scenario assumptions must be accessible. Individual inputs should not be persisted; batch uploads stay in memory, are validated before scoring, and offer a download rather than a database.

## Research limits

The search is targeted and source-informed, not exhaustive. The research did not reproduce external metrics, verify external deployments, audit all code or notebooks, or establish a broad license for competition data. Public availability is not a guarantee of data origin, representativeness, fairness, or commercial-use permission. All results claimed for this college project must come from this repository's own executed pipeline and saved evidence.
